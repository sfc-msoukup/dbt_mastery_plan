Chapter 1

The Three-Numbers Problem

Why analytics teams adopt dbt, what it really does, and the project you will build

The Scenario

Monday, 9:00. The CEO has three screens up. Q3 2026 return on the Bitcoin position: the trading desk dashboard says +37.5%, the allocation report says +39.4%, the board deck says +35.4%. All three read the same raw price table in Snowflake. Nobody can say which is right. The meeting ends with: "One number, and proof, by Thursday."

Every number in this course is real. The raw rows are Bitstamp daily prices and Federal Reserve rates. The four answers above and below came from running the queries.

Before you read: commit to an answer

The raw table is identical for all three dashboards. What is the most likely cause of three different numbers?

Open each dashboard in the simulator and read the SQL behind it.

None of the three analysts made a typo. Each made a reasonable choice that nobody reviewed:

  • Trading desk added the daily returns. Returns multiply, though: +10% then +10% is +21%, not +20%.
  • Allocation report measured from the first close inside the quarter, so July 1 itself went missing. The starting point has to be the June 30 close.
  • Board deck compounded correctly, but joined to a Treasury-rate table that has no weekends. That join silently deleted 28 of 92 days.

The correct figure is +42.8%. Notice that nothing errored. Every one of these queries ran green.

The load-bearing idea of this course: dbt does not make your SQL smarter. It makes one definition the only definition, puts it through review, and proves it with tests every time it builds.

What dbt is

Common wrong model

"dbt is a data pipeline tool, so it pulls the data in and transforms it." It does not pull anything in. If you plan your project around dbt fetching files or calling APIs, you will end up with nothing that loads your data.

dbt (data build tool) is a compiler and a runner for SQL that already lives in your warehouse. You write each transformation as a SELECT in its own file. dbt then does five things:

  1. Compiles: it resolves template code (Jinja, Chapter 6) and references to other models into plain SQL.
  2. Wraps: it puts each SELECT inside DDL, such as CREATE VIEW AS or CREATE TABLE AS. Which DDL is decided by the model's materialization.
  3. Orders: it builds the models in dependency order. It works out that order from the references between files, which form a graph called the DAG.
  4. Tests: with dbt build, logic checks (unit tests) run before a model builds and data checks run right after it. If a check fails, everything downstream is skipped. (dbt run builds only and runs no tests; Chapter 4.)
  5. Documents: it generates documentation and a lineage graph from the same files.

All of the computing happens inside Snowflake; your data never passes through dbt. Getting data into Snowflake is a separate job, done with COPY INTO, Snowpipe, Openflow, Fivetran and similar tools. This split is called ELT: Extract and Load first, then Transform in the warehouse. dbt is the T.

Land Data, Write a Model

Load the raw files, set up a dbt project, and build your first model

The Scenario

Before you can fix the number, you need the raw data in Snowflake. There are two files. The crypto CSV has a website URL on its first line. The FRED CSV marks missing days with blank values. Step 1: Land the raw data (this is not dbt)

Everything in this step is plain Snowflake SQL. Its only job is to copy each file into a table, faithfully. Data cleaning happens later, in dbt.

  • Crypto: download Bitstamp_BTCUSD_d.csv and Bitstamp_ETHUSD_d.csv from CryptoDataDownload.
  • FRED: download https://fred.stlouisfed.org/graph/fredgraph.csv?id=DFF, then the same URL with DGS10 and with CPIAUCSL. Save them as fred_DFF.csv, fred_DGS10.csv and fred_CPIAUCSL.csv. The load below reads the series name from the file name.

Snowflake SQL (run once, as a role that can create databases)
-- 1. A home for the project, and a small warehouse that suspends itself
CREATE DATABASE IF NOT EXISTS DBT_MASTERY_LAB;
CREATE SCHEMA IF NOT EXISTS DBT_MASTERY_LAB.RAW;
CREATE WAREHOUSE IF NOT EXISTS DBT_LAB_WH
  WAREHOUSE_SIZE = 'XSMALL' AUTO_SUSPEND = 60 AUTO_RESUME = TRUE INITIALLY_SUSPENDED = TRUE;
USE WAREHOUSE DBT_LAB_WH;
USE SCHEMA DBT_MASTERY_LAB.RAW;

-- 2. Describe the two file shapes.
--    CryptoDataDownload puts a URL on line 1 and the header on line 2 -> skip 2.
CREATE OR REPLACE FILE FORMAT cdd_csv  TYPE = CSV SKIP_HEADER = 2 FIELD_OPTIONALLY_ENCLOSED_BY = '"';
CREATE OR REPLACE FILE FORMAT fred_csv TYPE = CSV SKIP_HEADER = 1;
CREATE OR REPLACE STAGE landing;

-- 3. Landing tables: raw values plus two audit columns (which file, when loaded)
CREATE OR REPLACE TABLE crypto_ohlcv (
  unix_ts NUMBER, trade_ts TIMESTAMP_NTZ, symbol VARCHAR,
  open FLOAT, high FLOAT, low FLOAT, close FLOAT, volume_base FLOAT, volume_usd FLOAT,
  _file VARCHAR, _loaded_at TIMESTAMP_LTZ);
CREATE OR REPLACE TABLE fred_observations (
  series_id VARCHAR, observation_date DATE, value VARCHAR,   -- VARCHAR on purpose: gaps arrive as ''
  _file VARCHAR, _loaded_at TIMESTAMP_LTZ);

-- 4. Upload the five files to the stage, then load. Either:
--    a) Snowsight: Ingestion > Add Data > Load files into a Stage, pick
--       DBT_MASTERY_LAB.RAW.LANDING, path crypto/ or fred/ (250 MB per file max), or
--    b) Snowflake CLI (snow sql) from your laptop:
-- PUT 'file:///path/to/Bitstamp_*.csv' @landing/crypto/;
-- PUT 'file:///path/to/fred_*.csv'     @landing/fred/;
COPY INTO crypto_ohlcv FROM (
  SELECT $1,$2,$3,$4,$5,$6,$7,$8,$9, METADATA$FILENAME, CURRENT_TIMESTAMP()
  FROM @landing/crypto/) FILE_FORMAT = (FORMAT_NAME = 'cdd_csv');
COPY INTO fred_observations FROM (
  SELECT REGEXP_SUBSTR(METADATA$FILENAME, 'fred_([A-Z0-9]+)\\.csv', 1, 1, 'e'),  -- series id from file name
         $1, $2, METADATA$FILENAME, CURRENT_TIMESTAMP()
  FROM @landing/fred/) FILE_FORMAT = (FORMAT_NAME = 'fred_csv');

-- 5. The role dbt runs as. It reads RAW and creates its own schemas; nothing more.
CREATE ROLE IF NOT EXISTS TRANSFORMER;
GRANT USAGE ON WAREHOUSE DBT_LAB_WH TO ROLE TRANSFORMER;
GRANT USAGE, CREATE SCHEMA ON DATABASE DBT_MASTERY_LAB TO ROLE TRANSFORMER;
GRANT USAGE ON SCHEMA DBT_MASTERY_LAB.RAW TO ROLE TRANSFORMER;
GRANT SELECT ON ALL TABLES IN SCHEMA DBT_MASTERY_LAB.RAW TO ROLE TRANSFORMER;
GRANT SELECT ON FUTURE TABLES IN SCHEMA DBT_MASTERY_LAB.RAW TO ROLE TRANSFORMER;  -- tables you add later
GRANT ROLE TRANSFORMER TO USER <your_user>;
Gotcha 1: the header is on line 2. The CryptoDataDownload file starts with a URL banner, and the column names are on the second line. With SKIP_HEADER = 1 the load fails on the header row: Numeric value 'unix' is not recognized ... line 2. You need SKIP_HEADER = 2.
Gotcha 2: FRED gaps are empty strings. On days a series did not publish, FRED's CSV has an empty value. The 10-year Treasury file (DGS10) has 720 of them. That is why value is landed as VARCHAR: the landing table keeps the file exactly as it arrived, and the cleaning rule is written once, in staging. (Older material says FRED uses a '.' for gaps. The current CSV export does not.)

The files grow by one row a day, so expect a little more than the lab's counts: 4,337 BTC rows starting 2014-11-28 and 3,260 ETH rows, taken in October 2026. Check the start dates, which never change. The _file and _loaded_at columns record which file each row came from and when it landed. You will use _loaded_at in Chapter 4.

Step 3: Declare the raw tables as sources

dbt needs to know which tables it did not build. A source is a YAML declaration of a table that something else loads. Models read sources with {{ source('raw', 'crypto_ohlcv') }} rather than a hardcoded name. That way the raw tables show up in lineage, and dbt can check whether they are still being refreshed (the freshness block, covered in Chapter 4).

models/staging/_sources.yml
sources:
  - name: raw
    database: DBT_MASTERY_LAB
    schema: RAW
    description: "Landing tables loaded by COPY INTO. dbt never writes here."
    config:
      loaded_at_field: _loaded_at
      freshness:
        warn_after: {count: 2, period: day}
        error_after: {count: 4, period: day}
    tables:
      - name: crypto_ohlcv
        description: "Bitstamp daily OHLCV for BTC and ETH from CryptoDataDownload."
        columns:
          - name: symbol
            description: "Pair, e.g. BTC/USD"
          - name: trade_ts
            description: "Bar open time, UTC"
      - name: fred_observations
        description: "FRED series, one row per series per observation date. Missing values arrive as empty strings."

Step 4: Your first model

A model is a .sql file that contains exactly one SELECT. The file name becomes the name of the object dbt creates. Here is the staging model for crypto prices:

models/staging/stg_crypto__daily_prices.sql
with source as (
    select * from {{ source('raw', 'crypto_ohlcv') }}
),

renamed as (
    select
        split_part(symbol, '/', 1)  as asset_code,
        trade_ts::date              as price_date,
        open                        as open_usd,
        high                        as high_usd,
        low                         as low_usd,
        close                       as close_usd,
        volume_usd
    from source
)

select * from renamed
-- the newest row is today's bar, still trading: its "close" is just the latest tick
where price_date < current_date()
  • One job per CTE. source reads the raw table and renamed renames and casts columns. Each step can be read on its own.
  • split_part(symbol, '/', 1) turns BTC/USD into BTC. This is what lets one model handle every asset.
  • where price_date < current_date() drops today's bar. The newest row in the file is a day that is still trading, so its "close" is just the latest price. Put that rule anywhere downstream and every "today" number would keep changing all day.
  • The naming pattern stg_<source>__<entity> (with a double underscore) is a widely used dbt convention. It tells you the layer and the source at a glance.

Compile first, then run

dbt compile turns your files into plain SQL under target/compiled/ without executing anything. dbt run also wraps that SQL in DDL and executes it. Here is what compile turns {{ source('raw','crypto_ohlcv') }} into:

target/compiled/.../stg_crypto__daily_prices.sql (excerpt)
select * from DBT_MASTERY_LAB.RAW.crypto_ohlcv

After dbt run, a second copy appears under target/run/. It is the statement that was actually executed, with the DDL wrapper added:

target/run/.../stg_crypto__daily_prices.sql (excerpt)
create or replace view DBT_MASTERY_LAB.dbt_mike_staging.stg_crypto__daily_prices as (
    with source as (
    select * from DBT_MASTERY_LAB.RAW.crypto_ohlcv
    ), ...
);

When the SELECT logic is wrong, read target/compiled/. When the object is wrong (wrong schema, view instead of table), read target/run/. Now run the model with dbt run -s stg_crypto__daily_prices. The -s flag selects which models to run.

ref() and the DAG

How dbt decides what to build first, where each model lands, and how to select part of the graph

Three more nodes

Staging for FRED follows the same pattern as crypto. The one difference is the gap rule from Chapter 2, which lives here, once:

models/staging/stg_fred__observations.sql
with source as (
    select * from {{ source('raw', 'fred_observations') }}
),

cleaned as (
    select
        series_id,
        observation_date,
        -- FRED marks a missing observation with an empty string
        try_to_double(nullif(value, '')) as value
    from source
)

select * from cleaned
where value is not null

nullif(value, '') turns an empty string into NULL, try_to_double casts the text to a number (returning NULL instead of failing on bad input), and the final filter drops the gaps.

A seed is a small CSV file kept in the repo. dbt seed loads it as a table. Use seeds for reference data that people edit through code review, such as asset names or risk tiers, never for data feeds:

Seeds in practice: load, query, reference, reload

The seeds: block above sends every seed to its own schema. Load the CSV with:

expected output
$ dbt seed
1 of 1 OK loaded seed file dbt_mike_seeds.assets ... [INSERT 2]
Done. PASS=1 WARN=0 ERROR=0 SKIP=0 NO-OP=0 REUSED=0 TOTAL=1
  • Where it lands. The table is named after the file (assets) and goes in dbt_mike_seeds. That is the same schema-naming rule you will see below for staging. Query it like any table: select * from DBT_MASTERY_LAB.dbt_mike_seeds.assets;
  • How models read it. A seed is built by dbt, so you read it with {{ ref('assets') }}, never with source() and never by table name. It then appears in the DAG like a model. Chapter 4 tests every asset_code against it, Chapter 5 joins it into the mart for names and classes, and Chapter 7 snapshots it.
  • Column types. dbt infers a type for each column from the CSV. Here all four columns are text, so the inference is safe. If a column ever holds codes with leading zeros, such as 0012, inference would turn them into numbers. Pin the type in YAML with the seed's column_types config.
  • Editing it. Change the CSV, commit it, and run dbt seed again. dbt reloads the rows into the existing table. If you add, remove or rename a column, run dbt seed --full-refresh so dbt drops and recreates the table with the new columns. dbt build also loads seeds, in DAG order, before anything that refs them.
  • What does not belong here. Prices, rates, or anything a system produces. Those arrive through the loader and are declared as sources. A seed is for a short list that a person edits through code review, like this one.

Here is the first model that builds on another model. It reads staging through ref(), never by table name:

models/intermediate/int_crypto__daily_returns.sql (Chapter 3 version)
with prices as (
    select * from {{ ref('stg_crypto__daily_prices') }}
)

select
    asset_code,
    price_date,
    close_usd,
    (close_usd / nullif(lag(close_usd) over (partition by asset_code order by price_date), 0) - 1) as daily_return
from prices

What ref() actually does

Common wrong model

"ref() is a shortcut for typing a table name." If that were all it did, a hardcoded name would be harmless. It is not: a hardcoded name compiles and runs successfully while quietly breaking two things.

{{ ref('stg_crypto__daily_prices') }} has two jobs:

  1. It records an edge in the DAG. dbt reads every ref() and source() call before it runs anything, and builds a graph from them. That graph sets the build order. It is also what selectors such as + walk. A hardcoded name creates no edge, so a downstream model can build first, or be left out of a selection.
  2. It resolves the right schema for the current target. The compiled SQL above points at dbt_mike_staging because the target was dev. The same file run against prod points at analytics_staging. A hardcoded name always points at whichever schema you typed. If that is the production schema, which it usually is, every dev run reads production data and the test in your sandbox proves nothing about your own changes.

Here is the selector in action: the dbt ls output above lists staging plus the one model built on it so far. By the end of Chapter 5 the same command lists four. With a hardcoded name it would list only one.

Where models land: schema concatenation

Your profile's schema is dbt_mike, and the staging folder sets +schema: staging. Most people expect the views in staging. They actually land in dbt_mike_staging. dbt's default naming rule is <target schema>_<custom schema>. That is what keeps five developers from overwriting each other: Sarah's views land in dbt_sarah_staging. In prod the target schema is analytics, so the same folder builds analytics_staging. Some teams override the macro that does this (generate_schema_name) so that prod uses the bare names. That is a deliberate, project-wide decision; leave the default alone until you need something else.

Key Takeaways

  • ref() records a DAG edge (for build order and selection) and resolves the schema for the current target. A hardcoded name breaks both, without any error.
  • source() marks tables dbt does not build; ref() is for everything the project builds, seeds included.
  • Seeds are small, version-controlled CSVs for reference data, never data feeds. dbt seed loads them into <target>_seeds, models read them with ref(), and a column change needs dbt seed --full-refresh.
  • Custom schemas are concatenated: target dbt_mike plus +schema: staging gives dbt_mike_staging.
  • A trailing + selects children, a leading + selects parents, and dbt ls previews a selection.
Chapter 4

Tests That Stop Bad Data

Data tests, custom tests, unit tests, source freshness, and what a failure does to a build

The Scenario

Two weeks ago a NULL closing price got into staging, and every return after it came out NULL. The dashboard showed a blank chart and nobody noticed until a meeting. Last week someone "fixed" the return formula, and it was wrong in the fourth decimal place. You want both mistakes caught by the build, before anything reaches a dashboard.

Before you read: commit to an answer

dbt runs a not_null test as a SQL query. When does the test pass?

This single rule is how every dbt test works, including the ones you write yourself.

Data tests: a query that returns the bad rows

A data test is a SELECT that returns the rows that break a rule. Zero rows means the test passes; any rows mean it fails. For example, not_null on close_usd compiles to roughly select close_usd from ... where close_usd is null. dbt ships four generic tests that you attach to columns in YAML: unique, not_null, accepted_values and relationships. The last one checks that every value appears in another model, like a foreign key.

models/staging/_staging.yml

dbt build: tests run inside the DAG

dbt run builds models and runs no tests at all. dbt build runs seeds, models, snapshots and tests together in DAG order. Each test runs right after the node it checks, and a failure skips that node's children. Branches that don't depend on it carry on. One thing catches people out: a data test runs after its node, so when it fails, that node has already been rebuilt with the bad rows, and only its children are protected. A unit test runs before its model, so a unit-test failure skips the model itself, and the old version stays. Keeping a bad build out of production is a separate job, done in CI (Chapter 8). Try it:

Each test has a severity. The default, error, fails and skips the node's children. warn logs the failure and lets the build continue. Use warn only when a named person reviews the warnings on a schedule. Otherwise a warning is just a failure that nobody reads.

The Scenario

Now you can answer the Monday question. You need one daily table of returns per asset, with that day's interest rate attached. Then you need one quarterly number per asset, tested so that nobody has to take it on trust. The board deck's mistake from Chapter 1 is waiting for you here.

Grain: what one row means

The grain of a table is the answer to "one row per what?" Crypto rows are one per asset per calendar day, seven days a week. The 10-year Treasury rate (DGS10) has one row per business day. The fed funds rate (DFF) is published every day, and CPI once a month. Join two tables with different grains without thinking about it, and you either lose rows or multiply them.

This is exactly the board deck's bug from Chapter 1. Its +35.4% was compounded correctly over the wrong 64 days.

The fix: a date spine, then forward-fill

A date spine is a table with exactly one row per calendar day. You left-join each rate onto the spine, so every day exists and days with no published value come out NULL. Then you forward-fill: replace each NULL with the most recent published value, so a Saturday carries Friday's rate. The result has a daily grain and joins cleanly to crypto. Here is int_macro__daily_rates, written out in plain SQL:

models/intermediate/int_macro__daily_rates.sql (Chapter 5 version)
-- Chapter 5 version: written out by hand. Chapter 6 replaces the repetition with a loop.
-- One row per calendar day from the first crypto bar (Nov 2014) to yesterday
with days as (
    select row_number() over (order by seq4()) - 1 as n
    from table(generator(rowcount => 10000))
),

spine as (
    select dateadd(day, n, '2014-11-01'::date) as date_day
    from days
    where dateadd(day, n, '2014-11-01'::date) < current_date()
),

observations as (
    select * from {{ ref('stg_fred__observations') }}
),

-- 1. Long to wide: one column per series, NULL on days a series did not publish
wide as (
    select
        spine.date_day as rate_date,
        max(case when observations.series_id = 'DFF' then observations.value end) as dff,
        max(case when observations.series_id = 'DGS10' then observations.value end) as dgs10,
        max(case when observations.series_id = 'CPIAUCSL' then observations.value end) as cpiaucsl
    from spine
    left join observations
        on observations.observation_date = spine.date_day
    group by spine.date_day
),

-- 2. Forward-fill: carry the last published value across gaps (weekends, holidays, monthly CPI)
filled as (
    select
        rate_date,
        last_value(dff ignore nulls) over (
            order by rate_date rows between unbounded preceding and current row
        ) as dff,
        last_value(dgs10 ignore nulls) over (
            order by rate_date rows between unbounded preceding and current row
        ) as dgs10,
        last_value(cpiaucsl ignore nulls) over (
            order by rate_date rows between unbounded preceding and current row
        ) as cpiaucsl
    from wide
)

select * from filled
  • Long to wide: FRED arrives as one row per series per date. max(case when series_id = 'DFF' then value end) turns each series into its own column (a pivot), one row per date.
  • Forward-fill: last_value(x ignore nulls) over (order by rate_date rows between unbounded preceding and current row) means "the most recent non-NULL value up to and including today."
  • The spine: generator makes 10,000 numbered rows, and dateadd turns each number into a date. row_number() is used because seq4() alone can skip values.
  • The CASE and LAST_VALUE lines repeat once per series. Chapter 6 replaces both blocks with one loop over a project variable.

The governed number

Common wrong model

"A quarter's return is the sum of its daily returns." Returns compound: +10% then +10% is 1.1 × 1.1 − 1 = +21%. Adding them gives the trading desk's +37.5% instead of +42.8%.

models/marts/mart_quarterly_returns.sql
-- One governed definition of "quarterly return": compound the daily returns
with daily as (
    select * from {{ ref('fct_daily_asset_returns') }}
),

by_quarter as (
    select
        asset_code,
        date_trunc('quarter', price_date)::date as quarter_start,
        count(*)                                as trading_days,
        exp(sum(ln(1 + daily_return))) - 1     as quarterly_return,
        avg(fed_funds_rate_pct)                 as avg_fed_funds_rate_pct
    from daily
    group by 1, 2
)

select
    by_quarter.*,
    assets.asset_name,
    assets.asset_class
from by_quarter
inner join {{ ref('assets') }} as assets
    on assets.asset_code = by_quarter.asset_code

exp(sum(ln(1 + r))) - 1 is the product of every (1 + r), minus 1, written in a form SQL can aggregate. (SQL has no product aggregate, but summing logs and exponentiating gives the same result.) The join to the assets seed adds names and classes, so dashboards never hardcode them.

Being right is not enough; it has to be provably right. A singular test is a single .sql file in tests/ that checks one specific rule against the real data. This one recomputes every quarter a second way, from prices: the last close divided by the close just before the quarter, minus 1. The two only agree when the chain of daily returns has no missing day, which is exactly what goes wrong when a join drops rows. It returns any quarter where the two disagree:

tests/assert_quarterly_return_reconciles.sql
-- Compounded daily returns must equal (last close / close before the quarter) - 1.
-- Any row returned is a quarter where the two definitions disagree.
with daily as (
    select * from {{ ref('fct_daily_asset_returns') }}
),

bounds as (
    select
        asset_code,
        date_trunc('quarter', price_date)::date as quarter_start,
        max_by(close_usd, price_date)            as last_close,
        min_by(close_usd / (1 + daily_return), price_date) as prior_close
    from daily
    group by 1, 2
)

select
    bounds.asset_code,
    bounds.quarter_start,
    mart.quarterly_return,
    bounds.last_close / bounds.prior_close - 1 as price_based_return
from bounds
inner join {{ ref('mart_quarterly_returns') }} as mart
    using (asset_code, quarter_start)
where abs(mart.quarterly_return - (bounds.last_close / bounds.prior_close - 1)) > 1e-9

dbt uses Jinja, a templating language from Python. Jinja runs before any SQL does. Its output is plain text, and that text is the SQL that gets sent to Snowflake. There are only three delimiters:

{{ ... }}Prints a value into the SQL{{ ref('stg_fred__observations') }}, {{ s | lower }}

"Jinja understands my data." Jinja knows nothing about the warehouse. It only produces text. Put a series in the list that was never loaded, and the SQL compiles and runs perfectly, with an all-NULL column. Generated SQL needs tests just as much as hand-written SQL does.

Macros: give repeated logic a name

A macro is a Jinja function stored in macros/. You can call it from any model. This one gives "the percentage change from the previous row in the same partition" a single definition:

macros/pct_change.sql
{% macro pct_change(column, partition_by, order_by) %}
    ({{ column }} / nullif(lag({{ column }}) over (partition by {{ partition_by }} order by {{ order_by }}), 0) - 1)
{% endmacro %}

And here it is in use. Compare this source with the compiled version you saw in Chapter 3:

models/intermediate/int_crypto__daily_returns.sql
with prices as (
    select * from {{ ref('stg_crypto__daily_prices') }}
)

select
    asset_code,
    price_date,
    close_usd,
    {{ pct_change('close_usd', 'asset_code', 'price_date') }} as daily_return
from prices

When should something become a macro? When the same logic would otherwise be copied into two or more models, and you can give it a clear name. A project where every model is mostly macro calls is hard to read and hard to review. One small, well-named macro like this is the sweet spot.

Incremental and Snapshots

Process only what changed, and keep a history of things that get overwritten

The Scenario

The fact table holds about 7,600 rows today, and every run rebuilds all of them. The PM now wants hourly bars for 20 coins, which is millions of rows rebuilt every hour. Separately, the risk committee changed ETH from high to medium risk, and wants to know which tier applied on any past date. The seed only stores the current value.

Incremental: merge the recent window, keep the rest

Here is the fact table from Chapter 5, now incremental. Two things are new: the config(...) block at the top and the {% if is_incremental() %} filter. The rest is unchanged:

models/marts/fct_daily_asset_returns.sql
{{ config(
    materialized='incremental',
    unique_key=['asset_code', 'price_date'],
    incremental_strategy='merge',
    on_schema_change='fail'
) }}

with returns as (
    select * from {{ ref('int_crypto__daily_returns') }}
    where daily_return is not null
    {% if is_incremental() %}
      -- re-process a few days so late corrections to recent bars are merged in
      and price_date >= (
          select dateadd(day, -{{ var('incremental_lookback_days') }}, max(price_date)) from {{ this }}
      )
    {% endif %}
),

rates as (
    select * from {{ ref('int_macro__daily_rates') }}
)

select
    returns.asset_code,
    returns.price_date,
    returns.close_usd,
    returns.daily_return,
    rates.dff                                   as fed_funds_rate_pct,
    rates.dgs10                                 as treasury_10y_pct,
    -- crypto trades 365 days a year, so de-annualise the cash rate over 365
    returns.daily_return - rates.dff / 100 / 365 as excess_return
from returns
left join rates
    on rates.rate_date = returns.price_date
  • materialized='incremental': on the first run, dbt builds the whole table. On every later run it only processes the rows that the filter lets through.
  • is_incremental() is true only when the table already exists and you did not pass --full-refresh. That is why the filter sits inside an {% if %}.
  • {{ this }} is the table being built, so the filter means "from 3 days before my latest date onward." The 3 is var('incremental_lookback_days'); add incremental_lookback_days: 3 under vars: in dbt_project.yml.
  • unique_key plus incremental_strategy='merge': rows whose key matches an existing row are updated, and the rest are inserted. The 3-day lookback re-reads recent days so that late price corrections overwrite the old values.
  • on_schema_change='fail': if the columns of the SELECT change, stop instead of quietly altering the table.

The simulator walks through what each kind of change does.

incremental_strategyWhat it does in SnowflakeUse when
appendINSERT the new rows onlyImmutable events, where duplicates are impossible or acceptable

Two rules come with incremental models. After a logic change, run --full-refresh. And size the lookback to how late your source can correct data. A 3-day window silently misses a correction to a bar from 10 days ago.

The dynamic_table materialization from Chapter 1 is a different trade-off. Instead of you writing the incremental filter, Snowflake decides how to refresh, to stay within a target_lag.

Snapshots: history of values that get overwritten

Common wrong model

"The incremental table keeps history." It does not. A merge overwrites the matching row. An incremental table is a performance technique, not a record of how values changed.

A snapshot compares a source to its previous run. When a tracked column changes, it closes the old row (setting dbt_valid_to) and opens a new one. This pattern is called Slowly Changing Dimension Type 2 (SCD2). From dbt 1.9 you can declare snapshots in YAML:

snapshots/assets_snapshot.yml
snapshots:
  - name: assets_snapshot
    relation: ref('assets')
    config:
      schema: snapshots
      unique_key: asset_code
      strategy: check
      check_cols: ['risk_tier']
      hard_deletes: invalidate
  • strategy: check compares the values in check_cols. Use strategy: timestamp with updated_at: instead when the source has a trustworthy last-modified column; it is cheaper.
  • hard_deletes: invalidate closes the row if the key disappears from the source. This setting replaced the older invalidate_hard_deletes.

Key Takeaways

  • An incremental model filters with is_incremental() and {{ this }}, then merges on unique_key. In the lab, the rerun touched 8 rows instead of 7,591.

3. Contracts: a model's shape becomes a promise

Someone adds risk_tier to the mart's SELECT, which nobody downstream expects. Tests check values. What stops the new column from shipping?

Tests check the values in the rows; a contract checks the table's shape (its columns and their types).

models/marts/_marts.yml
groups:
  - name: markets
    owner:
      name: Markets Analytics
      email: markets-analytics@example.com

models:

          - type: not_null

4. Slim CI inside Snowflake

Snowflake SQL (Slim CI inside Snowflake)
-- The PR branch's files go to their own stage and their own object, targeting ci.
-- From the PR branch's deploy copy:
--   snow stage copy ./deploy @DBT_MASTERY_LAB.OPS.dbt_src_pr --recursive --overwrite
CREATE OR REPLACE DBT PROJECT DBT_MASTERY_LAB.OPS.MARKET_ANALYTICS_PR
  FROM '@DBT_MASTERY_LAB.OPS.dbt_src_pr'
  DBT_VERSION = '1.12.3'
  DEFAULT_TARGET = 'ci';

-- Mount the artifacts of the PROD object's last successful run as ./imports/state,
-- then build only what this branch changed, reading prod for everything else.
EXECUTE DBT PROJECT DBT_MASTERY_LAB.OPS.MARKET_ANALYTICS_PR
  ARGS = 'build --select state:modified+ --defer --state ./imports/state --target ci'
  IMPORTS = (
    SYSTEM$DBT_GET_LAST_SUCCESSFUL_RUN_TARGET('DBT_MASTERY_LAB.OPS.MARKET_ANALYTICS') AS 'state'
  );

IMPORTS mounts the artifacts of a previous run (including manifest.json) at ./imports/state. That replaces the "save the prod manifest somewhere" step from Chapter 8. The calling role needs MONITOR on the production object, and that object must have had a successful run within the last 7 days.

Gotcha 2: "last successful run" means any run. This is why step 3 gives dev runs their own object. In the lab they first ran on the prod object, and its most recent successful run was a one-model dev run, so CI compared against the wrong state. Depending on what the dev run touched, you get either "Nothing to do" (a silent pass) or, as on the second day, an error deferring to dev schemas that were never built. Keep CI state on an object that only ever runs production builds, or name an exact run with SYSTEM$LOCATE_DBT_ARTIFACTS(<query_id>).

Key Takeaways

  • The same project files deploy as a DBT PROJECT object and run with EXECUTE DBT PROJECT plus ARGS, against Snowflake only.
  • No credentials are needed: account and user can be empty. The profile role is further limited to the caller's grants. Set threads, or the run uses 1.
  • env.yml environments resolve before dbt starts, including "{{ select ... }}" queries run in the caller's session. ENVIRONMENT on EXECUTE overrides the object's default, which overrides the file's default.
  • Pin DBT_VERSION. The account default (1.9.4 here) rejected 1.10.5+ syntax.
  • Tasks need a user-managed warehouse (no serverless), and they start suspended.
  • IMPORTS provides CI state, from the last successful run of any kind, so keep it on a prod-only object.
  • Packages need an external access integration for dbt deps, unless dbt_packages/ ships with the project.
